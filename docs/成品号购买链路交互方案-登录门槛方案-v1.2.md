> 读者：接下来执行开发的 AI 工程师

> 范围：成品号购买链路（弹窗 + 抽屉合并为单抽屉）；下单入口的登录动作；抽屉内的余额抵扣口径
> 定位：**纯前端 Demo 样式改造**。不接后端、不做真实支付、不做真实鉴权。

## TL;DR

1. 现状是两个问题叠在一起：**居中 Dialog（确认购买）→ 右侧 Sheet（支付订单）两层浮层、信息和确认动作各重复一遍**；以及**未登录也能一路走到支付，抽屉里还给游客显示「可用余额 $359.96 / 余额抵扣」**。
2. 目标形态：**彻底删掉居中 Dialog**，商品卡「立即购买」直接打开右侧抽屉；把「确认购买」和「选择支付方式」**压成同一个 stage**，整条链路的界面态从 4 个降到 3 个（确认下单 → 链上支付 → 完成），商品名 / 单价 / 数量 / 合计全链路只出现一次。
3. 登录不再做任何拦截浮层：**未登录点下单入口 → 直接沿用系统既有的一键 mock 登录 → 紧接着打开抽屉**，全程不弹新浮层、不新增登录 UI。
4. 实现上有一条硬要求：**不要改 `components/payment-experience.tsx` 的 `PaymentExperience`**（钱包充值、代充向导、批量工作台都在用它），新建独立的 `AccountPurchaseSheet`。
5. 代充向导 / 批量工作台本轮**只接入同一个登录动作**，不动它们的 5 步交互结构。

**额外核对结论（会改变实现选择，务必先看）：**

- **A. `PaymentExperience` 被 3 处复用**：`PaymentFlowSheet`（本方案目标）、`components/recharge-wizard.tsx:306`、`components/recharge-batch-flow.tsx:182`（后两处内嵌在 `.wizard-unified-payment` 里）。→ **改它的 stage 机 = 顺手改坏代充向导和批量工作台**。所以新建组件。
- **B. `app/page.tsx:1220-1241` 的弹窗 `else` 分支不是死代码**：`openPurchase` 只把 `recharge && brand === "chatgpt"` 引导进向导，**`claude-pro-recharge` / `claude-max-recharge` 会落到 `setSelectedProduct`，走这个 else 分支**。→ 新抽屉必须同时承载这两类商品（规则见 §1.8）。
- **C. 抽屉里现显示的「订单号」是假的**：`confirmPurchase` 先 `MO...` 造一个号再开抽屉，也就是说这个订单在用户点「支付」之前根本不存在。→ 合并后首段不显示订单号，订单号只在链上支付段出现。
- **D. `@media(max-width:760px)` 是一个共享块**（`app/globals.css:692`）：除了 `.payment-flow-sheet` 的宽，里面还压着 11 条公共规则（`.payment-setup-view` 等 `padding:20px`、`.payment-network-grid,.crypto-payment-panel{grid-template-columns:1fr}`、`.payment-qr-card{order:-1}`、`.order-payment-product` 降 2 列、`.payment-quick-amounts{repeat(2,1fr)}`、`.payment-timeline` 横向可滚、`.payment-demo-controls` 竖排）。→ **这个块一行都不能动**（见 §1.9、§5.8）。
- **E. `handleDemoLogin` 不能直接拿来给购买场景用**：里面有一句无条件的 `setSelectedMenu("home")`，会把用户从「购买账号」页踢回首页 → 需要拆出一层纯登录动作（见 §2.2）。

## 1. 目标交互方案（弹窗 + 抽屉合并）

### 1.1 方向确认与三处修正

team-lead 倾向的「直接开右侧抽屉、抽屉内用 stage 分段」**成立**，但要修正三点，否则达不到用户要的效果：

1. **不是"抽屉内 stage 分段"就够了。** 如果抽屉里再排 4 段（确认 → 选支付方式 → 链上详情 → 完成），用户经历的界面态数量**一个都没少**（还是 4 个）。真正的减法是：**把「确认购买」和「选择支付方式」合并成同一段**。用户抱怨的"两层信息重复"根因就是这两段各自带一份商品+金额。
2. **不要复用 `PaymentExperience` 的 stage 机**（原因见 §0-A）。新建 `components/account-purchase-sheet.tsx`。
3. **居中 Dialog 整个删除**，不保留做二次确认（理由见 §1.4）。

为什么是抽屉而不是弹窗、也不是全屏页：

- 成品号购买是"在商品列表里顺手做的一件事"，用户需要保持商品上下文；抽屉右侧滑出不打断列表阅读，弹窗是打断式。
- 项目已有成熟的抽屉视觉与交互语言（`.payment-flow-sheet`、`product-editor-sheet`、`order-detail-drawer`），统一到抽屉比新造一套弹窗样式成本低。
- 反向验证（抽屉降级成弹窗）：链上支付详情含二维码 + 收款地址 + 倒计时 + 模拟按钮，塞进 520px 弹窗会挤成一条长滚。

### 1.2 合并后的抽屉形态

- **组件**：新增 `components/account-purchase-sheet.tsx`，导出 `AccountPurchaseSheet`
- **触发**：商品卡「立即购买」
- **容器**：`<Sheet open={...} onOpenChange={...}><SheetContent side="right" className="payment-flow-sheet is-purchase">`
  - **复用 `.payment-flow-sheet`**，只加 modifier `.is-purchase`（理由：该类的 header sticky、padding、浅灰底全部可复用，避免第二套样式值；这是"扩成共用"而非"复制一套"）。**同一套写法项目里已有先例**：`app/globals.css:925` 的 `.topup-card.is-pay .crypto-payment-panel{grid-template-columns:minmax(0,1fr)}`，照这个走。
  - `.is-purchase` 覆盖三件事（基础，不限断点）：宽度 `min(760px, calc(100vw - 24px))`；`.crypto-payment-panel` 单栏纵排；`.payment-qr-card` `order:-1`
  - **宽度为什么从 860px 降到 760px 且固定不变**：合并后首段不再需要两栏；宽度在 stage 之间变化会让抽屉边缘来回跳，正好是用户抱怨的"视线横向跳"。链上支付段用单栏纵排（二维码卡在上、明细在下），宽度恒定。
  - ⚠️ `.is-purchase .payment-qr-card{order:-1}` 在 ≤760px 时与共享块里的同名规则**重复**，这是无害的（共享块那条约 760px 以下生效，我们的基础规则覆盖全部宽度），保留即可，不要为此去改共享块。
- **标题**：`SheetTitle` 全 stage 固定 = `content.purchaseSheetTitle`（「购买账号」），不随商品变
  - 理由：标题随 stage 或商品变化会造成 header 高度/宽度跳动；描述行已经承载了当前阶段信息
- **描述**：`SheetDescription` 随 stage 切换（3 条文案，见 §3）
- **stage 枚举**：`type PurchaseStage = "confirm" | "chain" | "success"`（3 个，不是 4 个）
- **stage 切换时把抽屉滚动容器 `scrollTo({ top: 0 })`**，否则从长首段滚到底部点支付后，链上段会停在中间位置

### 1.4 关闭交互语义

| 交互 | stage `confirm` | stage `chain` | stage `success` |
|---|---|---|---|
| 点遮罩 | 关闭并丢弃 | 关闭并丢弃 ＋ toast | 关闭并重置 |
| 按 Esc | 同上 | 同上 | 同上 |
| 右上角 ✕ | 同上 | 同上 | 同上 |
| 底部次要按钮 | 取消并丢弃 | —（无此按钮） | —（无此按钮） |

- **关闭 = 放弃订单，不做二次确认。** 理由：Demo 无真实扣款，且 `ProductOrder` 在点主按钮之前根本不存在（现在那个订单号是提前造出来的假号，见 §0-C）——给一个还不存在的订单做"确认放弃"是把风险演反了。真正有风险的节点是链上转账，而 stage `chain` 已有倒计时 + 收款地址 + 「仅支持 XX 网络」警示。
- **stage `chain` 关闭时给一次 toast**：`content.purchasePayInterrupted`（「已离开支付页，本次支付单不再有效。」）。理由：收款地址已经展示过，用户可能已经转账，这是整条链路唯一"退出有现实含义"的地方，成本只有一行。
- **草稿不保留**：关闭即 `setPurchaseProduct(null)` + `setPurchaseQuantity(1)` + `setPurchaseStage("confirm")` + `setPurchaseIntent(null)`。理由：跨会话草稿需要持久层，而本项目只做前端 Demo；用 `sessionStorage` 模拟只会多一串状态分支、多一条说不清的验收项。
- 关闭后重新点「立即购买」：数量回到 1、无残留支付单、stage 回到 `confirm`。

### 1.5 stage `confirm`：分区清单与顺序

容器沿用 `.payment-setup-view`（`display:grid; gap:20px`），分区从上到下：

1. **商品条** — 复用 `.order-payment-product`
   `品牌 mark（小号）` + `商品名` + `副标题` + 右侧 `单价（$499 + /账号）`
2. **数量区** — 复用 `.quantity-row` / `.quantity-control`
   - 标题 `content.quantityLabel`（「购买数量」）
   - 副信息：`purchase` 模式 → `${currentStockLabel} ${stock} · ${maxQuantityLabel} ${limit} ${accountUnit}`；`preorder` 模式 → `${maxReservationLabel} ${limit} ${accountUnit}`
   - 增减器：`−` / 数字 / `+`；`quantity <= 1` 时 `−` disabled，`quantity >= limit` 时 `+` disabled
   - `limit === 1` 时**不渲染增减器**，副信息直接写「限购 1 个账号」口径
3. **购买说明** — 复用 `.purchase-notes`，仅 `businessType === "account"` 渲染
   `购买说明` 标题 + 列表：`purchaseNoteOfficial` / `purchaseNoteOrder` / `purchaseNoteBatch` / `credentialFormatDescription` /（`preorder` 时追加）`preorderNote`
4. **售后说明** — 复用 `.after-sales-note`，仅 `businessType === "account"` 且 `afterSalesDescription` 存在时渲染
5. **金额明细** — 复用 `.payment-breakdown`
   行序：`商品金额` →（`effectiveBalance > 0` 时）`可用余额` →（`effectiveBalance > 0` 时）`余额抵扣` → `is-total` 行
   `is-total` 行标题：余额足额 → `content.totalLabel`（「应付金额」）；余额不足 → `待支付`
6. **抵扣说明一行小字** — 复用 `.payment-auto-deduction`
   - 只在 `effectiveBalance > 0 && effectiveBalance < total` 时渲染：`账户余额将自动抵扣，仅需支付剩余 $139.04。`
   - 其余情况（余额为 0、余额足额）**不渲染这一区**
   - ⚠️ v1.2 已删除原来的 `!isLoggedIn → guestBalanceHint` 分支：抽屉只可能以登录态出现，游客态不可达（见 §2.3）
7. **支付方式** — 复用 `.payment-section` + `.payment-network-card`
   - 余额足额 → 渲染 `.payment-balance-method` 单行卡（`✓ 平台余额` + `支付后剩余 $x`）
   - 余额不足 / 余额为 0 → `请选择补差额方式` 标题 + 两张网络单选卡（TRC20 / ERC20），**默认选中 TRC20**
   - `quantity` 每变化一次都要重算 5/6/7 三区（数量变化会翻转余额关系）
8. **底部动作条（sticky，`position:sticky; bottom:0`）** — 类名 `.purchase-sheet-actions`
   - 左：`content.cancel`（「取消」）→ 直接挂 **`.page-back-button`**（共用类，40px 高、白底、1px 边框）
   - 右：主按钮 → 挂 **`.payment-primary-action`**
   - 主按钮文案 = `content.purchasePayAction`（「支付」）+ 金额 `<span>`（金额由代码渲染，**不可编辑**，结构对齐现在 `.dialog-confirm` 的 `content.confirmPurchase` + `<span>$499</span>`）
   - 金额口径：余额足额 → `$499.00`；余额不足 / 余额为 0 → `139.0400 USDT`（跟随所选网络，沿用 `usdt()` 的 4 位小数口径）
   - **主按钮不再叫「确认购买」**：合并后没有第二层确认，再叫"确认购买"会让人以为后面还有一步。统一为「支付 $x」，动作明确。
   - 首段点主按钮的两种去向：余额足额 → 直接进 `success`；否则 → `createPaymentIntent` 后进 `chain`
   - **防重复点击**：主按钮点击后立刻 `disabled`，直到 stage 切换完成

### 1.6 stage `chain`：链上支付

- 直接复用 `CryptoPaymentPanel`（`components/payment-experience.tsx:79`），**不改动它**，参数与现在一致：`intent` / `onIntentChange` / `onComplete`；`demoCollapsible` 默认 false（保留内联的 Demo 状态按钮）；`countdownLabel` / `countdownHint` 不传
- 单栏纵排：二维码卡 `.payment-qr-card` `order:-1`（在数据之上）
- 顶部次要返回：`content.purchaseBackToMethod`（「返回修改支付方式」）→ 回 stage `confirm`，并 `setPurchaseIntent(null)`
  - 再次点主按钮会**重新生成支付单**（与现状 `beginCryptoPayment` 每次 `createPaymentIntent` 行为一致），不沿用上一张，避免出现"支付单还在有效期但界面已回到确认页"的双重状态
- 成功回调 → 进 `success`（复用现有的 `applyPaymentCompletion(completion)`，`app/page.tsx:667`）

### 1.7 stage `success`：支付完成

复用现有 `.payment-success-view` 版式：`CheckCircle2` 图标 + `content.purchaseSuccess`（「支付成功」）+ 商品名 + `content.purchaseSuccessDescription` + `.payment-success-summary`（订单金额 / 支付方式 / 余额抵扣 / 链上支付）＋ `payment-success-actions`：

- `查看订单` → `navigateTo("orders")`（会自动关掉抽屉，因为 `navigateTo` 会清 `purchaseProduct`，见 §5）
- `返回商品页` → 关抽屉，`setSelectedBrand(product.brand)`，停留在 `account` 页

### 1.8 异常态与边界态

| 场景 | 判定 | 表现 |
|---|---|---|
| 已售罄 | `getPurchaseMode(product) === "soldout"` | 卡片按钮 `disabled`（现状已如此），不进抽屉 |
| 预售 | `getPurchaseMode(product) === "preorder"`（含 `stock === 0` 且 `status === "available"`） | **不进抽屉、不弹任何浮层**。点「立即预定」→ 直接 `toast.success(content.reservationSuccess, { description: content.reservationSuccessDescription })`，**不产生订单**。（现状是先弹窗再 toast，白多一层浮层，改掉） |

## 2. 登录方案（v1.2 重写）

### 2.1 结论：不做拦截浮层，点击即沿用系统既有的一键登录

用户原话：「登录的方案，你参考一下其他页面的现状，系统已经有的东西保持一致即可，没必要创新。」

核对结果：系统里**唯一的登录实现**就是 `handleDemoLogin()` 那一句话 —— 没有登录页、没有登录表单、没有登录浮层（见 §0）。所以本方案**不新增任何登录 UI**，直接复用它。

**选定行为：** 未登录用户点下单入口（「立即购买」/「立即选购」/「批量办理」）→ **先自动完成既有的一键 mock 登录，再继续原本的分支**（`preorder` → 照旧直接 toast；`purchase` → 打开抽屉）。全程不弹新浮层，用户感知就是"点一下，抽屉直接开了"。

顺带把游客自带余额的问题一起收了：因为"下单即登录"，**游客态抽屉不可达** —— 抽屉永远只以登录态出现。

### 2.2 具体逻辑

- `openPurchase(product)` 内：未登录时**先执行登录动作，再走原有分支**。不 `return`、不设 pending、不弹层。
- `openPurchase` 的 `recharge && brand === "chatgpt"` 分支、`openBatchRecharge()`（`app/page.tsx:713`）同样在执行前先过同一个登录动作。
- **不新增任何登录 UI**：不新建 `components/login-required-dialog.tsx`，不要 `loginPromptOpen` state，不要 `pendingPurchase` state，不要"登录后恢复原意图"这套机制（没有浮层，就没人会中途跑去顶部登录）。
- **游客仍然可以自由浏览商品列表** —— 顶部导航「购买账号」「套餐升级」和落地页全部 CTA 保持现状，门槛只作用在"下单动作"上。

### 2.3 一个必须写清的坑：`handleDemoLogin` 不能直接复用

`handleDemoLogin()` 里有一句无条件的 `setSelectedMenu("home")`。如果购买场景直接调它，用户会被从「购买账号」页**踢回首页**，然后抽屉开在首页上方 —— 这显然不对。

所以要求拆一层（改动点见 §5.2）：

```
// 新增：纯登录动作，不跳页
const signInDemo = () => { setIsLoggedIn(true); toast.success(<沿用系统现有文案>); };
// 原有函数改为复用
const handleDemoLogin = () => { signInDemo(); setSelectedMenu("home"); };
```

- toast 文案**沿用系统现有的那句**（现为硬编码 `"登录成功（Demo）"`），**不要新增 content key、不要改顶部登录的现有行为**。
- `handleDemoLogin` 对外的行为必须与现在**完全一致**（顶部导航点登录仍然回首页），这是零回归要求。
- 购买 / 代充场景**只用 `signInDemo()`**。

### 2.4 连带简化：游客态 UI 分支整块删掉

因为 §2.1 的"下单即登录"，**游客态抽屉不可达**，所以：

- **删** `guestBalanceHint` 这条文案 key（原 §3.1 第 9 条）及所有引用
- **删** 原"游客态抽屉不渲染余额行 / 不出现平台余额选项"这类 UI 分支描述；§1.5 分区 6 里 `!isLoggedIn → guestBalanceHint` 那一支一并删除（分区 6 只保留"余额不足时的一行抵扣小字"）
- **删** 原"游客态引导文案""未登录态 topup 页不出现余额"这几条验收项（场景不可达，留着会让工程师想办法去构造一个到不了的状态）

**但 `effectiveBalance` 这个派生保留**：

```
const effectiveBalance = isLoggedIn ? walletBalance : 0;
```

理由：`walletBalance`（`app/page.tsx:519`）的初值直接取 mock 的 `accountDashboardSummary.availableBalance`（359.96），与登录态完全无关 —— 这是"游客自带余额"的根因。用一个派生把它收口在一处，成本 1 行，且万一以后新增下单入口漏接登录动作，也不会露富。`walletBalance` state 本身**不动**（保持 359.96），因为它被 `applyPaymentCompletion`（`app/page.tsx:667`）用于账目累加，改初值会造成登出/登入后余额跳变。

传递口径：`effectiveBalance` 传给 `AccountPurchaseSheet` / `RechargeWizard` / `WalletRechargePage` / `AccountDashboard`。

### 2.5 代充链路是否纳入

**结论：纳入，同样只做"入口接同一个登录动作 + 余额口径用 `effectiveBalance`"，不改它的交互结构。**

理由：

- 同一问题在代充链路里同样成立：`openPurchase`（`app/page.tsx:639-644`）对 `recharge && brand === "chatgpt"` 直接 `setWizardProduct(product)` 进向导，无任何登录校验；`openBatchRecharge`（`app/page.tsx:713`）也一样；向导内 `recharge-wizard.tsx:306` 的 `PaymentExperience` 会拿到 `availableBalance`（未登录时也是 359.96）并渲染「可用余额 / 余额抵扣」。
- 但代充向导是一个 5 步沉浸式工作区（`components/recharge-wizard.tsx`，另有 `components/recharge-batch-flow.tsx` 批量工作台），重构它超出本次需求范围，而且会显著放大回归面（向导自带离开确认、批量任务生成、订单联动）。
- 所以最小改动：
  - `openPurchase` 的 `recharge` 分支前过一遍 `signInDemo()`
  - `openBatchRecharge`（`app/page.tsx:713`）同样
  - 向导 / 批量工作台 / topup 页拿到的 `availableBalance` 换成 `effectiveBalance`
  - 向导内部的付款步骤（`recharge-wizard.tsx:305` 的 `.wizard-unified-payment`）**不改结构**

### 3.2 改值的 key（key 保留，改默认值 **＋ 改写存量迁移**）

| key | 原默认值 | 新默认值 | 存量迁移（`app/page.tsx:559-560`） |
|---|---|---|---|
| `purchaseSuccess` | 购买信息已确认 | 支付成功 | **必须改成链式迁移**：`if (v === "Demo：商品购买成功" \|\| v === "购买信息已确认") → "支付成功"` |
| `purchaseSuccessDescription` | 交互演示已完成，不会发起真实支付。 | 交互结果只写入前端 Mock，不会发起真实支付。 | **必须改成链式迁移**：`if (v === "这是交互演示，不会创建订单或发起支付。" \|\| v === "交互演示已完成，不会发起真实支付。") → "交互结果只写入前端 Mock，不会发起真实支付。"` |

**为什么必须改迁移代码（这会真出 bug，不是洁癖）：**

`app/page.tsx:559-560` 现在是「单跳迁移」，只认**上一轮之前的旧值**：

```
if (config.content.purchaseSuccess === "Demo：商品购买成功") config.content.purchaseSuccess = "购买信息已确认";
```

后果：任何**已经打开过页面**的用户，localStorage 里 `purchaseSuccess` 现在存的是「购买信息已确认」（上一轮迁移写进去的）。这个值：
- 不等于旧值 `"Demo：商品购买成功"` → 不触发迁移
- 也不等于新默认值「支付成功」→ 而 `defaultContent` 只在**首次访问 / 点了「恢复默认」**时才被采用

**所以这批老用户会永远卡在「购买信息已确认」，新默认值只对全新用户生效。** 结果就是同一个完成段，老用户看到「购买信息已确认」、新用户看到「支付成功」—— 文案分裂。`purchaseSuccessDescription` 同理。

**修法：把这两行改成链式迁移**（把"上一轮的目标值"也当成需要迁移的旧值）：

```
if (["Demo：商品购买成功", "购买信息已确认"].includes(config.content.purchaseSuccess)) config.content.purchaseSuccess = "支付成功";
if (["这是交互演示，不会创建订单或发起支付。", "交互演示已完成，不会发起真实支付。"].includes(config.content.purchaseSuccessDescription)) config.content.purchaseSuccessDescription = "交互结果只写入前端 Mock，不会发起真实支付。";
```

这样新老用户都收敛到同一份文案，且**用户自己手动改过的值不会被覆盖**（只匹配已知旧值）。

> 后续凡是改 `defaultContent` 里已有的默认文案，都要顺手检查这一区是否有对应的单跳迁移行，需要就链式补一跳，否则每次改文案都会重演一次。

## 6. 约束条款（硬性，开发必须遵守）

1. **长三元链铁律**：`app/page.tsx` 的主内容是一条 `selectedMenu === "xxx" ? ... :` 长三元链（约 998–1103 行）。**任何沉浸式子视图都不许用局部状态短路这条链**，必须写成 `selectedMenu === "xxx" && localState`。项目已因此踩坑两次（充值页、代充向导）。本方案的购买抽屉是 `Sheet` 浮层，**不要**把它塞进这条链。
2. **导航入口一律复用 `navigateTo()`**（`app/page.tsx:698`），它会清 `wizardProduct` / `wizardInitialMode` / `paymentRequest`（本次还要加清购买态）。不要新写 `setSelectedMenu` 直调。
3. **不要改 `PaymentExperience`**（`components/payment-experience.tsx:185`）。它同时服务钱包充值、代充向导（`recharge-wizard.tsx:306`）、批量工作台（`recharge-batch-flow.tsx:182`）。要改支付相关逻辑，改新组件，或者只改 `CryptoPaymentPanel` 的入参。
4. **共享 media 块不许动**：`app/globals.css` 的 `@media(max-width:760px)`（`:692`）与 `@media(max-width:460px)`（`:693`）同时服务钱包充值页与代充向导。新组件的窄屏适配**只能新增 `.is-purchase` 自己的断点**。
5. **改默认文案必须检查存量迁移**：`app/page.tsx:537-568` 那一段 localStorage 兼容迁移是「单跳」写法（只认上一轮的旧值）。凡是改 `defaultContent` 里**已有**的文案，都要顺手看这一段有没有对应的迁移行 —— 有就补一跳链式迁移，否则**老用户会永远卡在旧文案**（`purchaseSuccess` 已经踩过一次，见 §3.2）。
6. **不许自造新交互**：登录沿用系统既有实现（`handleDemoLogin` 那一套），不新增登录页 / 登录表单 / 登录浮层；系统里已经有的交互模式一律保持。这是本次用户明确给的方向。
7. **页头 / 返回按钮 / 主卡 / token 统一**：
   - 页头用 `.uc-page-heading`
   - 返回按钮一律用**共用类** `.page-back-button`（40px 高、白底、1px 边框、16px 图标 + 14px/600），**不要另写第二套**

10. **视觉语言统一**：新分区优先把既有的 `.topup-*` / `.recharge-*` / `.payment-*` / `.page-back-button` 选择器**扩成共用**，而不是复制一套新的样式值。本方案里 `.payment-flow-sheet.is-purchase` 就是这个思路的示范（与 `.topup-card.is-pay` 同一套写法）。
11. **文案必须可编辑**：新增文案放进 `data/content.ts`，通过 `EditableText` 渲染；新组件必须接收并透传 `editMode` / `updateContent`。
12. **信息去重硬指标**：商品名 / 副标题 / 单价 / 数量 / 合计金额在购买链路上各只允许出现一次（验收 §4-A）。
13. **不要顺手清理无关代码**：`.purchase-dialog*` 之外的历史样式、`selectedMenu === "orders"` 的 placeholder 分支等，都不属于本次改动范围。

| # | 议题 | 裁定 | 落点 |
|---|---|---|---|
| 1 | 登录方案怎么做？ | **复用系统既有的一键登录**（用户裁定）。不新增任何登录 UI、不弹拦截浮层；未登录点下单入口 → 先 `signInDemo()` → 继续原分支。`handleDemoLogin` 拆出纯登录动作以便购买场景使用，对外行为零变化 | §2、§3.1、§5.2 |
