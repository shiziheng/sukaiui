# SUKAI 前端 Demo → 后端接口契约梳理

> 用途：拿去和后端开发对齐接口。本文把"前端现在用 Mock 撑起来的数据需求"翻成"后端要实现的接口清单"。
> 结论先看：当前是纯前端 Demo，**没有任何网络请求**；`data/*.ts` 里的 TS 类型就是现成的接口返回体草案，可直接复用。

---

## 1. 项目现状（对齐前提）

| 项 | 现状 | 对接口的影响 |
|---|---|---|
| 技术栈 | React 19 + Vinext(Next 兼容层跑 Vite) + Tailwind 4 + shadcn/Radix | 前端是 SPA 心智，接口走 JSON/REST 最顺 |
| 路由 | 只有根路由 `/`（`app/page.tsx`），业务"页面"是 `selectedMenu` 这个 useState 切换，**不是 URL 路由** | 先不用纠结 RESTful 路径，按"资源/操作"谈接口即可 |
| 数据访问 | 直接 `import` `data/*.ts` 静态数组，**无 api/client 封装、无 fetch、无 useQuery** | 前端需要新增一层 API client 来替换这些 import |
| 状态管理 | 纯 `useState`，钱包余额/订单/登录态都在内存，**刷新即丢**；`localStorage` 只存文案编辑配置 | 登录态、余额、订单列表都要后端兜底盘活 |
| 鉴权 | `vite.config.ts` 的 `mockAuth` 中间件写死测试用户；UI 上是 `setIsLoggedIn(true)` 假登录 | 真实鉴权方案需和后端定（见 §5 待确认） |
| 数据库 | `db/schema.ts` 是空的，Drizzle 已接好 D1 但没表 | 后端建表可参考 §2 的字段 |

## 2. 前端数据 Schema = 接口返回体（直接复用）

后端建表和写返回体时，下面这些类型就是草案，建议**字段名保持一致**，前端改造成本最低。

### 2.1 商品 / 品牌 / FAQ
- `Brand`（`data/brands.ts`）：`id: "chatgpt"|"claude"`, `name`, `logo`, `logoWatermark`, `accentColor`
- `Product`（`data/products.ts`）：`id`, `businessType: "account"|"recharge"`, `brand`, `name`, `subtitle`, `tags[]`, `price`, `priceSuffix?`, `discountLabel?`, `features[]`, `stock?`, `stockText`, `status: "available"|"soldout"`, `fulfillment?: "instant"|"preorder"`, `maxQuantity?`, `credentialFormatDescription?`, `afterSalesDescription?`, `highlight?`, `highlightLabel?`
- `FAQGroup`/`FAQItem`（`data/faqs.ts`）：按 `businessType + brand + productId?` 分组，item 含 `question/answer/sortOrder/enabled/defaultOpen/linkText?/linkUrl?`

### 2.2 用户中心 / 钱包（`data/account-dashboard.ts`）
- `user`: `name`, `email`, `initials`, `status`
- `summary`: `totalBalance`, `availableBalance`, `frozenBalance`, `points`, `totalOrders`, `accountOrders`, `rechargeOrders`, `completedOrders`, `totalSpent`, `invitedUsers`, `totalRewards`
- 流水类：`balanceRecords[]` / `rechargeRecords[]` / `walletRecords[]` / `topUpRecords[]` / `frozenRecords[]`（字段：`id,title,amount,time,status,balance?,orderId?,note?`）
- `orders: DashboardOrder[]`：`id`, `kind:"account"|"recharge"`, `product`, `snapshot`, `amount`, `quotedAmount?`, `chargedAmount?`, `status:"completed"|"processing"|"pending"|"failed"`, `statusLabel`, `createdAt`, `failureReason?`
- 邀请：`invite{code,link,rate}`、`invitedUserRecords[]`、`inviteRecords[]`、`inviteTemplates[]`、`exchangeRecords[]`

### 2.3 订单管理（`data/order-management.ts`）
- `ManagedOrder`：`id`, `kind`, `productName`, `productMeta`, `amount`, `currency:"USD"`, `status`, `createdAt`, 以及三类详情其一：
  - `AccountOrderDetails`：`credentialAvailable`, `account?`, `password?`, `deliveredAt?`, `completedAt?`
  - `RechargeOrderDetails`：`email`, `currentPlan`, `targetPlan`, `quoteAmount`, `actualAmount: number|null`, `completedAt?`, `failureReason?`
  - `BatchOrderDetails`：`taskId`, `accountCount`, `taskStatus:"processing"|"partial"|"completed"`, `items[]{id,email,targetPlan,status,result}`
- 状态枚举（前后端必须对齐）：
  - 成品号：`account_pending / account_stocking / account_delivered / account_completed / account_cancelled`
  - 代充：`recharge_pending / recharge_processing / recharge_partial / recharge_success / recharge_failed`

### 2.4 支付（`data/payment-mocks.ts`）
- `PaymentIntent`：`id`, `orderId?`, `mode:"wallet_recharge"|"balance_payment"|"order_payment"`, `totalAmount`, `balanceApplied`, `cryptoAmount`, `uniquePayableAmount`, `network:"trc20"|"erc20"`, `status:"pending"|"detected"|"underpaid"|"confirming"|"completed"|"expired"|"failed"`, `receivedAmount`
- `PaymentCompletion`：`paymentIntent`, `newBalance`, `walletTransactions[]`, `rechargeRecord?`, `order?`, `overpaidAmount`
- `paymentNetworks`：TRC20 / ERC20 的收款地址（Demo 写死，`TQDemo8uK4...` / `0xSUKAI7Demo...`，**上线必须换成真实地址且不可写死在前端**）

### 2.5 代充 / 批量（`data/recharge-batch.ts`）
- `MAX_BATCH_SIZE = 100`
- `ImportedSession`: `{ session, note?, email? }`；支持 txt / csv / json 导入（`parseImportFile`）
- `BatchAccount`：`id`, `email: string|null`, `currentPlan: "Free"|"Plus"|"Pro"|null`, `targetPlan`, `parseStatus:"success"|"failed"`, `eligible`, `selected`, `failureReason?`
- `BatchTask`：`id`, `orderId`, `productName`, `targetPlan`, `accountCount`, `amount`, `status:"processing"|"partial"|"completed"`, `createdAt`, `items[]`

### 2.6 代充流程文案（`data/recharge-flows.ts`）
- `RechargeFlow`：`id`, `brand`, `steps[]`（登录→获取 Session→提交→支付→完成），`copy{}`（大量 UI 文案），`mockAccount{accountEmail,currentPlan,targetPlan,duration,verificationId}`, `paymentMethods[]`
- 注：目前 `copy{}` 全是前端写死文案；若想后台可配，需 `GET / PUT` 配置接口。

## 3. 接口清单（按优先级，带前端 mock 位置）

> 标注「前端当前」= 现在怎么骗过去的；「后端要做的」= 真实实现要点。

### A 组 · 交易与支付（最高优先级，涉及钱）
| # | 建议接口 | 用途 | 前端当前 | 后端要做的 |
|---|---|---|---|---|
| A1 | `POST /api/orders` | 创建订单（成品号/代充/批量） | `createBatchTask` + 购买弹窗 `confirmPurchase` | 落单、锁库存/冻结余额、返回 `ManagedOrder` |
| A2 | `POST /api/payments/intent` | 创建支付单（余额抵扣+USDT 差额） | `createPaymentIntent` | 计算 `balanceApplied/cryptoAmount`，下发**真实**充值地址+`uniquePayableAmount` |
| A3 | `POST /api/payments/{intentId}/confirm`（或链上回调） | 链上到账确认 | `completeMockPayment` + 按钮假"检测到交易" | 监听 TRC20/ERC20 入账，比对 `uniquePayableAmount`，回写余额/订单 |
| A4 | `GET /api/wallet/balance` + `GET /api/wallet/transactions` | 余额与流水 | `accountDashboardMock.summary/walletRecords` | 分页、按类型筛选 |
| A5 | `POST /api/wallet/recharge` | 钱包充值下单 | 复用 A2/A3 | 同支付链路 |

### B 组 · 代充与批量（核心业务差异点）
| # | 建议接口 | 用途 | 前端当前 | 后端要做的 |
|---|---|---|---|---|
| B1 | `POST /api/recharge/sessions/parse` | Session 解析与资格识别 | `mockParseSessions`/`buildMockAccount`（按字符串含 free/plus/pro 规则骗） | **真实读取账号**识别 `email/currentPlan`，判断 `eligible`（仅 Free 可办）；**严禁前端持久化 Session**（README 已声明） |
| B2 | `POST /api/recharge/batch` | 批量任务创建 | `createBatchTask` | 异步提交，返回 `taskId` |
| B3 | `GET /api/recharge/batch/{taskId}` | 批量任务进度 | `BatchTask.items` 静态 | 轮询/WebSocket 返回逐账号 `status/result` |

### C 组 · 订单与售后
| # | 建议接口 | 用途 | 前端当前 | 后端要做的 |
|---|---|---|---|---|
| C1 | `GET /api/orders?kind=&status=&keyword=&timeRange=&page=` | 订单列表/筛选/分页 | `orderManagementMock` + 本地过滤 | 服务端过滤+分页，返回 `ManagedOrder[]` |
| C2 | `GET /api/orders/{id}` | 订单详情+进度时间线 | `ManagedOrder` 静态字段 | 含 `accountDetails/rechargeDetails/batchDetails` |
| C3 | `POST /api/orders/{id}/cancel` | 取消订单 | `confirmCancel` 仅改 state | 校验可取消状态、释放冻结 |
| C4 | `GET /api/orders/{id}/credentials` | 凭据下发 | `accountDetails.account/password` 写死 | **加密/一次性**下发，敏感字段后端存 |

### D 组 · 用户 / 账户 / 安全
| # | 建议接口 | 用途 | 前端当前 | 后端要做的 |
|---|---|---|---|---|
| D1 | `POST /api/auth/login` · `register` · `GET /api/me` | 登录/注册/当前用户 | `handleDemoLogin` + `accountDashboardMock.user` | 真实鉴权；注意 ChatGPT `oai-authenticated-user-*` 头或自有账号体系 |
| D2 | `PUT /api/me/profile` | 编辑资料 | toast 占位 | 落库 |
| D3 | `PUT /api/me/password` | 修改密码 | `SecurityPage.save` toast | 校验旧密码 |

### E 组 · 营销 / 邀请 / 积分
| # | 建议接口 | 用途 | 前端当前 | 后端要做的 |
|---|---|---|---|---|
| E1 | `GET /api/invite/code` · `/records` · `/rewards` | 邀请码/记录/返佣 | `accountDashboardMock.invite*` 写死 `SHI-0001` | 生成码、绑定关系、返佣计算 |
| E2 | `POST /api/points/exchange` | 积分兑换余额 | toast 占位 | 落账、更新余额 |
| E3 | `GET /api/products` · `/brands` · `/faqs` · `/recharge-flows` | 商品/品牌/FAQ/流程配置 | `default*` 静态数组 | 若后台可配还需 `PUT` |

## 4. 前端对接改造建议（给后端同步，避免扯皮）

1. **新增 API client 层**：在 `lib/` 下建 `api/` 封装 `fetch`，集中处理 baseURL、鉴权头、错误码；替换 `app/page.tsx:50-60` 里那一堆 `data/*` import。
2. **Mock 切真开关**：建议用环境变量（如 `VITE_USE_MOCK`）控制走 mock 还是真接口，前期可并行联调。
3. **异步状态处理**：订单/批量任务/支付确认都是异步的，前端需补**轮询或 WebSocket**（C1/C2/B3/A3），不能像现在一次性同步拿到结果。
4. **敏感数据边界**：Session、密码、2FA、支付收款地址**绝不下发到前端常驻**，凭据走 C4 的一次性/加密接口。
5. **错误码约定**：订单失败原因（`failureReason`）、支付状态（`PaymentStatus` 7 态）前后端用同一套枚举。

## 5. 带去和后端对齐的待确认问题（Open Questions）

1. **鉴权方案**：走 ChatGPT OAuth（`oai-authenticated-user-*` 头）还是自有账号体系？影响 D1 和所有需登录的接口。
2. **Session 解析后端怎么实现**：是否真去读账号？`eligible` 规则（仅 Free 可办）是否后端定？B1 是合规红线，必须明确。
3. **USDT 支付监控**：后端怎么监听 TRC20/ERC20 入账？回调还是前端轮询？`uniquePayableAmount` 怎么保证对账唯一？A2/A3。
4. **凭据安全**：成品号账号密码怎么存、怎么下发（一次性链接？加密 token？）。C4。
5. **批量任务**：100 个账号的充值任务是否全异步？进度查询频率/推送方式。B2/B3。
6. **库存与冻结**：成品号库存是真库存还是虚拟？下单冻结/释放逻辑。A1/C3。
