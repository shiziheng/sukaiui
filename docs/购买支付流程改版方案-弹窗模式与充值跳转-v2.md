## TL;DR

1. **容器换掉**：购买浮层从右侧抽屉（`Sheet`）改回**居中弹窗**（`Dialog`）。上一轮删掉的 `.purchase-dialog-account` 视觉规格可以从 git HEAD 原样恢复（§7.5 里已把完整规格抄出来了），不需要重造。
2. **支付简化**：余额够 → 直接扣余额成交；余额不够 → **不再走"链上补差额"**。购买链路里的 `chain` 段整段删掉，连带删掉网络选择、"余额抵扣"行、"账户余额将自动抵扣…"提示条，以及成功页的「链上支付」「多支付已计入余额」两行。用户明确说"不需要考虑多付、少付"。
3. **充值跳独立页**：余额不足时点「去充值 $139.04」→ 关闭弹窗、**挂起这笔订单**、跳到现有钱包充值页（`selectedMenu === "topup"`）。充值成功后，**充值页的成功态出现一个「返回订单继续支付」按钮**，点了就跳回商品页并自动重开弹窗、恢复商品与数量，此时余额已够，主按钮变成「支付」。
4. **不做自动跳回。** 充值成功后不强制把用户弹回订单——给按钮让用户自己按。理由见 §3.3。
5. 三条硬约束：**不要改 `PaymentExperience`**；**不要动共享 media 块**（`@media(max-width:760px)` / `460px`）；**`navigateTo` 的调用要带参数**（§4.2，这是本次唯一有技术风险的点）。

### 0.1 三个关键事实

**A. 余额支付这条路已经通了，不用动支付 mock。** `completeMockPayment`（`data/payment-mocks.ts:109`）在 `mode === "balance_payment"` 时：`creditedAmount = 0`、`orderDebit = intent.totalAmount`、`newBalance = availableBalance - totalAmount`，并返回 `order: { ...order, paymentStatus: "paid" }`。

**B. 充值回写也已完整。** 同一个函数对 `mode === "wallet_recharge"`：`creditedAmount = receivedAmount`、`orderDebit = 0`、`newBalance = availableBalance + received`，并生成一条 `topUpRecord`。所以充值完成后 `walletBalance` 会自动涨，`balanceSufficient` 自动翻转。

**C. `navigateTo` 会清购买态——这既是问题也是解法。** 点「去充值」时我们希望"关掉弹窗但保留挂起订单"，所以不能裸调 `navigateTo`（它会把 `pendingOrder` 的思路打断）。见 §4。

## 1. 目标流程

```
商品卡「立即购买」
  └─ 居中弹窗打开，系统自动算金额、自动判余额
       │
       ├─【余额充足】availableBalance >= total
       │    ├─ 明细：商品金额 / 可用余额 / 应付金额
       │    ├─ 状态卡：✓ 平台余额 · 支付后剩余 $341.96
       │    └─ 主按钮「支付 $18.00」
       │         └─ 扣余额 → 弹窗切成功态
       │
       └─【余额不足】availableBalance < total
            ├─ 明细：商品金额 / 可用余额 / **还需充值 $139.04**
            ├─ 警示卡：⚠ $139.04 · 当前余额不足，充值到账后即可完成支付。
            └─ 主按钮「去充值 $139.04」
                 ├─ 关闭弹窗
                 ├─ **挂起这笔订单**（productId + quantity）
                 └─ 跳转钱包充值页（selectedMenu = "topup"，金额预填缺口额）
                      └─ 完成充值
                           ├─ 充值成功态出现「返回订单继续支付」（主按钮）
                           └─ 点击 → 跳回商品页 + 自动重开弹窗 + 恢复商品与数量
                                └─ 此时余额已够，明细总额行变「应付金额」
                                   └─ 用户点「支付」→ 扣余额 → 成功态
```

**一句话口径**：整条链路里"付钱"只有一个动作——**扣钱包余额**。链上转账只存在于"给钱包充值"这一步，而它现在是一个**独立页**，不是购买弹窗的一部分。

## 2. 购买弹窗规格

### 2.1 容器

- **组件**：新建 `components/account-purchase-dialog.tsx`，导出 `AccountPurchaseDialog`；**删除** `components/account-purchase-sheet.tsx`
- **类型**：`export type PurchaseStage = "confirm" | "success";`（只有两段）
- **根元素**：
  ```
  <Dialog open={Boolean(product)} onOpenChange={...}>
    <DialogContent className="purchase-dialog-account">
      <DialogHeader>…</DialogHeader>
      <div className="purchase-dialog-body">…各分区…</div>
      <div className="purchase-dialog-actions">…取消 / 主按钮…</div>
    </DialogContent>
  </Dialog>
  ```
- **宽度**：`min(560px, calc(100vw - 32px))`。比原弹窗（520px）宽 40px，给警示卡和明细多留点呼吸感；仍然明显是"弹窗"而不是面板。

### 2.2 必须做成「固定头 / 滚动体 / 固定脚」三行

**这是本方案唯一不能省的布局要求。** 弹窗只有 560px 宽，内容（商品条 + 数量 + 4 条购买说明 + 售后 + 明细 + 余额状态卡）竖着叠起来会超过一屏。如果不做三行结构，**「去充值」按钮会掉到折线以下，用户看不见**——那就等于把整个流程堵死了。

## 3. 充值跳独立页 + 回到订单

### 3.1 跳过去

弹窗内点「去充值 $139.04」→ 调 `onGoTopup(productId, quantity)` → `app/page.tsx`：

```
const goTopupForOrder = (productId: string, quantity: number) => {
  setPendingOrder({ productId, quantity });
  // ⚠️ 必须带 keepPendingOrder，否则 navigateTo 会把刚挂起的订单清掉（同一批次里后者覆盖前者）
  navigateTo("topup", { keepPendingOrder: true });
};
```

`navigateTo` 会在这一句里关掉弹窗（它清 `purchaseProduct` / `purchaseStage` / `purchaseIntent`）——**这正是我们要的效果**，不需要单独写关弹窗逻辑。

**充值金额预填**：把 `pendingOrder` 对应的缺口额（`product.price × quantity − effectiveBalance`，向上取整到整数、最小 1）传给 `WalletRechargePage` 的新 prop `initialAmount`。

> 为什么要向上取整：缺口可能是 139.04 这种小数，链上转账不友好；预填 140 让用户直接点或微调，比预填小数强。

### 3.2 充值页的改动（3 个可选 prop）

`components/wallet-recharge-page.tsx` 新增，**全部可选，默认行为一个字不变**：

| prop | 类型 | 作用 |
|---|---|---|
| `initialAmount?: number` | 可选 | 充值金额初始值。现在的 `useState(100)`（`:97`）改成 `useState(initialAmount ?? 100)` |
| `onResumeOrder?: () => void` | 可选 | 传入时，**成功态**额外渲染一个「返回订单继续支付」按钮；不传时成功态保持现状三按钮 |
| `pendingOrderHint?: string` | 可选 | 传入时，在页头下方渲染一条提示条（说明"当前正在为订单补足余额"） |

**成功态按钮调整**（仅在 `onResumeOrder` 存在时生效）：

| 按钮 | 传了 `onResumeOrder` | 没传（现状） |
|---|---|---|
| 返回订单继续支付 | **primary**（新增，排在最前） | 不渲染 |
| 继续充值 | outline | primary |
| 查看记录 / 返回钱包 | outline | outline |

> 注意 `useState(initialAmount ?? 100)` 的时机：`WalletRechargePage` 在 `selectedMenu === "topup"` 时才挂载（长三元链里条件渲染），从商品页跳过来时是**新挂载**，能正确取到初值。**不要**再加一个 `useEffect` 同步 `initialAmount`——那会在用户手动改过金额后把它冲掉。

### 3.3 回到订单：**用按钮，不自动跳**

充值成功后，**不自动把用户弹回订单**。理由：

1. 用户充完值可能还想看一眼充值记录、或者再充一点（余额不足时充少了要再充）。自动跳走会打断他。
2. 购买弹窗"毫无预兆地自己弹出来"是**惊吓**——用户可能已经不想买那个商品了。
3. 用户原话是"充值完成**可以**跳转回订单页面继续完成订单"——"可以"就是一个可选动作，按钮正好对上。

所以：成功态给「返回订单继续支付」按钮，用户按了才回。点了之后：

```
const resumePendingOrder = () => {
  const pending = pendingOrder;
  if (!pending) return;
  setPendingOrder(null);                                   // 先消费，避免重复触发
  const product = products.find((item) => item.id === pending.productId);
  if (!product) return;                                    // 商品没了就静默丢弃，不报错
  navigateTo(product.businessType === "recharge" ? "recharge" : "account");  // 先导航（会清购买态）
  setQuantity(pending.quantity);                           // ⚠️ 必须在 navigateTo 之后
  setPurchaseStage("confirm");
  setPurchaseIntent(null);
  setPurchaseProduct(product);                             // 弹窗自动重新打开
};
```

> ⚠️ **顺序陷阱（务必写死）**：`navigateTo` 会清 `purchaseProduct` / `purchaseStage` / `purchaseIntent`。所以"设弹窗状态"必须在"`navigateTo`"**之后**，否则刚设好的状态会被立刻清掉，弹窗不会出现。这个坑项目里已经踩过一次，别再踩。

回到商品页后，`walletBalance` 已经被 `applyPaymentCompletion` 更新过了，`balanceSufficient` 自动变成 `true`，明细总额行变「应付金额」、状态卡变「平台余额」、主按钮变「支付」——**这部分零代码，React 派生值自己就对了**。

### 3.4 挂起订单什么时候作废

| 时机 | 行为 | 理由 |
|---|---|---|
| `resumePendingOrder` 被调用 | 消费掉（先置 null） | 已完成使命 |
| 用户从充值页点了别的导航 | `navigateTo`（默认不带 `keepPendingOrder`）清掉 | 用户主动离开了，不该过一会儿又冒出来 |
| 用户退出登录 | 清掉 | 避免串到下一个"身份" |
| 用户回到商品页但没点按钮 | 保留 | 他可能一会儿还想去充 |

> 「订单列表加待支付 + 继续支付」的兜底**本轮不做**，理由见 §9 决策点 A。

## 4. `navigateTo` 的唯一改动

```
const navigateTo = (
  destination: DashboardDestination,
  options?: { keepPendingOrder?: boolean },
) => {
  setWizardProduct(null);
  setWizardInitialMode(null);
  setPaymentRequest(null);
  setPurchaseProduct(null);

  setPurchaseIntent(null);

};
```

- 只有 `goTopupForOrder` 会传 `{ keepPendingOrder: true }`。
- 其余所有调用方（顶部导航、`AccountDashboard onNavigate`、`handlePublicNavigation`、`onViewOrders`、`onExit`…）**一个字不改**，走默认值即"清挂起订单"，行为符合预期。

## 9. 决策点（请审核时拍）

### 决策点 A：要不要给订单列表加「待支付 + 继续支付」兜底？

**背景**：挂起订单能覆盖"去充值 → 回来"这条路，但覆盖不了"用户关掉弹窗、过一会儿想回来付"，也覆盖不了"用户直接从订单列表找那笔没付的单"。

- **选项 1（推荐 / 默认）：不做。** 理由：这轮目标是"简化 + 看效果"，加这一层会给 `data/order-management.ts` 的状态枚举、`getOrderActions`、`orders-page.tsx` 的 action 分发都加分支，还要给公共类型 `ManagedOrder` 加 `productId?: string` 才能反查商品。范围会明显变大。
- **选项 2：做。** 要点：
  1. `data/order-management.ts`：新增状态 `account_unpaid`（label「待支付」，tone `pending`，unified `processing`）；`accountStatusOptions` 加一条；`OrderActionId` 加 `"pay"`；`getOrderActions` 加 `case "account_unpaid"` → primary = `pay`
  2. `ManagedOrder` 加可选 `productId?: string`
  3. `components/orders-page.tsx`：新增可选 prop `onContinuePayment?: (order: ManagedOrder) => void`，渲染 `pay` 动作时触发
  4. `app/page.tsx`：弹窗打开时把订单写进 `generatedOrders`（状态 `account_unpaid`）；支付成功后把同 id 那条改成 `account_paid`；`onContinuePayment` 里按 `order.productId` 反查商品 → 恢复弹窗

### 决策点 B：成功态的「余额抵扣」怎么处理？

新版是 100% 余额支付，原「余额抵扣」的叙事（余额抵一部分、链上付一部分）已经不存在。

- **推荐**：改叫「余额支付」，新增 key `purchaseBalancePaidLabel`。改动一行，口径一致。
- 备选：直接保留旧文案不动（少加一个 key，但语义有点飘）。

### 决策点 C：充值页的「返回订单继续支付」放在成功态就够，还是要常驻？

现在只放在充值**成功态**。另一种做法是**充值页全程**顶部都显示一个「返回订单」入口（用户在充值中途改主意了也能回去）。

- **推荐**：只放成功态。理由：用户点「去充值」的意图就是"充完再付"，中途回去等于白跑；而且常驻入口会让充值页多一个与"钱包充值"这个通用场景无关的元素。
- 如果你觉得需要，我可以把 `pendingOrderHint` 那条提示条做成**带「返回订单」链接**的，成本很低。

### 决策点 D：弹窗宽度

原购买弹窗是 520px，我在方案里定 **560px**（内容比原来多了"余额状态卡"）。

- 想完全保持原样 → 说一声，改回 `min(520px, calc(100vw - 32px))`。
- 想要更宽（比如 600px）→ 也可以，但超过 600px 就不像"弹窗"了。

### 决策点 E：余额不足的警示卡配色

拟用**暖黄**（`#ead9ad` 边框 / `#fffaf0` 底，沿用项目既有 warning 色系，参考 `.payment-underpaid-card`）。要更醒目（红色边框）也可以说，但项目现有告警语言都是暖黄，换红色会破坏一致性。
